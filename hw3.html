The Caesar Cipher

Theory background

The Caesar Cipher was invented by the Roman Empire in the 1st century BC, taking the name from the emperor, to communicate secret messages to the army. Today, has no practical use other than for education.
Maybe the simplest method for encryption, it works by changing each letter with a shifted place correspondent. The shift quantity is fixed. An example: Caesar ⇛ Fdhvdu, with shift of 3 (the original value).

Implementation

The code to implement the cyphering is shown below. To encrypt or decrypt is enough to call the caesar_cipher function with the same value, remembering to use the negative shift for the back operation.


function caesar_cipher(message, shift = 3) {
  const regex_punctuation = /[^\w\s]+/g;
  let encrypted = "";

  // Lowercasing the letters
  message = message.toLowerCase()

  for (let l of message.split('')) {
    // No space nor punctuation shift
    encrypted += (l === ' ' || regex_punctuation.test(l)) ? l : String.fromCharCode(
      (l.charCodeAt(0) - 'a'.charCodeAt(0) + shift) % 26 + 'a'.charCodeAt(0)
    );
  }
  return encrypted;
}

Schemes comparison

The two presented schemes are very similar and different at the same time. Different certainly in the logic and mathematic involved in the process of key decision, encryption and decryption is much more sophisticated in elliptic-curve than caesar cipher. One uses a simple addition with PACMAN effect (modulo operation) and the other involve complex algebraic operations.

The similarity lies in the reduced key space for the encryption key (in this post's specific implementation). For the Caesar Cipher is composed of 26 possibilities for English text, the ECC example only 23. For distinct reasons, but pretty close and low for secure use. In case of much larger and planned ECC parameters the key space dimension skyrockets (otherwise, it would not been adopted in secure systems and cryptocurrencies).

From the statistical properties point of view, the encrypted message with Caesar Cipher maintains its letter frequency making it vulnerable to frequency attacks (PoC later in the post). For ECC this attack vector is not present thanks to the proper randomization of chipertexts.
Moreover, the message length before and after the encryption is a difference too. Caesar Cipher keeps the same length, whereas the implemented encryption with ECC (using AES CBC) does not. In fact, thanks to the AES use, the length of encrypted text if a multiple of 16 bytes.

Attacking the encryption

In this part, we will try to break the two schemes by exploiting their vulnerabilities in the right scenario.

Statistical Cryptanalysis of the Caesar Cipher

As mentioned before, a critical vulnerability of Caesar Cipher is the preservation of letters frequency in encrypted text. With a sufficiently large corpus of text in a known language (English for this experiment), it is possible to exploit and reverse the encryption.

let lf_ec = {};
let total_chars = 0;

for (let i = 'a'.charCodeAt(0); i <= 'z'.charCodeAt(0); i++)
  lf_ec[String.fromCharCode(i)] = ''

for (let i of Object.keys(lf_ec))

  (max, entry) => entry[1] > max[1] ? entry : max

// Calculate the key

Alternative attack vectors

A list of additional attack vectors:

  • The leak of the original message is enough to break the cryptographic scheme, which requires the change of shift quantity;
  • Brute force guessing the shift key. For each number from 1 to the number of letters in the specific language alphabet, try decrypting and check if correct. The check can be implemented by looking up the existence of the decrypted words;
  • Similar to the letter frequency, also the syllables frequency could indicate the shift quantity.

Ignoring the obvious inherited simplicity of a message leak, the other methods rely all on "intensive" computational workload and matching to existing statistical vocabularies. A clear limitation could be the presence of a large number of non-language existing words, such as acronyms, abbreviations, mixed letters, etc.
Comparing specifically the single letter and n-gram frequencies: I suppose better success rate for n-grams. Both because the need of smaller corpus, and the higher resistance to the previously mentioned limitation. However, n-grams are many more than letters, causing computational performance degradation.

Recovering the ECC private key/decrypting messages

After successfully breaking the Caesar Cipher with statistical cryptanalysis, we will try to exploit the reduced key size of the implemented example of ECC. In this case is not possible to copy the previous technique because, even the ECC "toy", has statistical protection.
We will make some assumptions instead, that in conjunction with the encryption implementation choices, open an opportunity for a PoC.

PoC description

The idea is to execute a brute force attack on a reduced quantity of possible private key values. Note that this dynamic is not suitable for properly configured ECC schemes (big value for p and G), due to the required computational power.
Let's assume that we have only the public knowledge properties (a, b, p, G, public key and AES nonce). Find the private key.
The theory states a single public key (Q) can be derived by multiple private keys (from the fact of subgroup being cyclic by the order value).
With the help of brute force, we can find a list of private key candidates. The problem is the number of candidates, infinite. To resolve the issue, the algorithm extracts only a fixed amount (not too few nor too many) of private keys.
Reached a dead end.
But, assume that we have an instance of message pair (clear text and corresponding encryption).
We can brute force check the right private key by decrypting successfully the message.
Note: if the last step does not return the recovered private key, then try to fetch more candidates.

Alternative attack vectors

The possible attack vectors for poorly or strongly configured schemes are many. From attacking the implementation around the ECC, to the mathematical concepts (less), up to future attack vectors (quantum computers brute force). In addition, there are a lot of side-channel attacks targeting the execution part of the operations (naming a few: timing, power, cache access, incomplete point-operation handling of edge cases, etc.)
A real example of a discovered implementation vulnerability affecting millions of computers running Windows in 2020 is CVE-2020-0601, called "CurveBall". A spoofing vulnerability in the validation of ECC certificates, gave the opportunity to attackers to use malicious executables with a valid certificate. In-depth analysis at https://www.sentinelone.com/vulnerability-database/cve-2020-0601/.

Regarding the presented ECC example implementation of this blog, a possibile vulnerability that would need further investigation is the error thrown when it encounters a vertical line (special points).
